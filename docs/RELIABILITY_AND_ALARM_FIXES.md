# 수집 안정성·판정 기준·경보 전환 수정 기록

작성일: 2026-11-08. 대상: `measurement-sync`.

1·2번은 `226136c`에 반영했고, 이번 변경은 3번 수정과 세 문제의 통합 검증을 포함한다. 새 화재 판별 AI를 추가한 작업은 아니다.

## 1. 통신만 이어지면 오래된 감지도 정상처럼 남던 문제

### 발생 상황과 영향

예를 들어 마지막 유효 판단은 10:00:00에 나왔는데, 이후 10초 동안 잘못된 CSI나 중복 프레임만 들어온다. 기존에는 통신을 받은 시각인 `Node.last_seen_at`이 계속 갱신돼 노드를 정상으로 표시했다. 실제로는 현재 상태를 알 수 없는데 과거 판단을 현재 판단처럼 사용할 수 있었다.

### 원인

수신 처리에서 접속 시각을 먼저 갱신하고 나서 파싱 실패·서브캐리어 불일치·중복 시간을 처리했다. 화면 상태는 접속 시각을 확인했지만 마지막 유효 `Inference.t`의 나이는 확인하지 않았다.

### 해결

- `app/services/state.py`에서 마지막 유효 판단의 시각도 확인한다.
- 유효 판단이 6초를 넘겨 갱신되지 않으면 노드는 `stale`, 이유는 `stale_inference`로 표시한다. 해당 구역에 다른 정상 노드가 없으면 `no_signal`(판단 불가)이 된다.
- 정상 데이터로 새 판단이 만들어지면 다시 정상 판단을 제공한다.
- 저수신율·재시작의 기존 제외 규칙과 종료된 상황·재생 완료 화면의 기록 보존은 유지한다.
- 판단 불가는 사람이 없다는 판정이 아니라, 현재 판단에 쓸 데이터가 없다는 뜻이다.

검증: `tests/test_inference_freshness.py`. 수정 전 invalid·duplicate·mismatch 세 경우가 실패했고, 수정 후에는 정상 복귀·6초 경계·기록 보존을 포함한 8개가 통과했다.

## 2. 보정 계산이 다른 수집 요청까지 기다리게 하던 문제

### 발생 상황과 영향

빈 방의 기준선을 계산할 때 전역 잠금을 잡은 채 계산했다. 기존 현장 기록의 20~26초 계산 동안 같은 잠금이 필요한 수집 요청도 기다려 수집기 전송이 시간 초과될 수 있었다. 다른 건물이나 노드의 요청도 영향을 받을 수 있었다.

### 원인

`finish_calibration()`이 배열 변환과 기준선 계산 전체를 잠금 안에서 수행했다. 수집 경로가 바깥 `RLock`을 잡은 채 자동 마무리를 호출하므로, 안쪽 잠금만 나누는 수정으로는 문제가 해결되지 않았다.

### 해결

1. 짧은 잠금 안에서 보정 실행 ID·노드·재시작 이력과 계산할 프레임을 확보한다.
2. 배열 변환과 기준선 계산은 수집 잠금과 DB 세션 밖에서 수행한다.
3. 결과를 저장할 때 잠깐 잠그고, 여전히 같은 보정인지·경보가 열렸는지·노드가 재시작했는지 다시 확인한다.

만료된 보정의 자동 계산은 별도 작업에서 실행한다. 같은 보정의 중복 요청은 계산을 다시 시작하지 않는다. 조회와 수집 요청은 계산 완료를 기다리지 않는다. 명시적인 `/calibration/stop`은 기존처럼 완료를 기다린다.

계산 중인 보정 대상의 새 프레임에는 `accepted: 0, reason: processing`으로 응답한다. 이미 확보한 보정 구간에 새 프레임을 섞지 않는 처리이며, 모든 프레임을 계속 저장한다는 뜻은 아니다. 다른 수집 요청은 계속 처리한다.

계산 도중 새 보정이나 경보가 시작되면 옛 결과를 적용하지 않는다. 노드가 재시작하면 그 노드의 계산 결과를 버린다. 한 노드의 계산 오류가 다른 노드나 다음 보정을 막지 않도록 정리한다.

검증: `tests/test_calibration_concurrency.py`. 수정 전 수집·조회 대기 두 경우가 실패했다. 수정 후 중복 종료·재시작·새 보정·경보·계산 예외·최초 자동 마무리를 포함한 8개가 통과했다. 테스트는 대기 이벤트로 계산을 멈춰 둔 동안 다른 요청이 완료되는지 확인한다. 수정 후 실제 보드의 처리 속도를 측정한 결과는 아니다.

## 3. 판정 기준 안내와 실제 동작, 경보 전환이 어긋나던 문제

### 3-1. 같은 상황을 서로 다른 기준으로 설명

모델 없는 실측·재생은 감지 0.50 / 가능성 0.20을 사용했지만, 모델 카드의 실행 기준 안내는 항상 0.70 / 0.35를 반환했다. 예를 들어 평활된 신호 변화 판정값 0.60은 화면에서는 '변화 큼'인데 안내를 따르면 '가능성 있음'으로 읽혔다. 이 값은 사람 존재 확률 60%라는 의미가 아니다.

판정 정책을 `app/services/detection.py`로 모으고 화면·첫 감지 기록·기준 안내가 같은 정책을 사용하도록 했다. 기준값 자체는 아래와 같이 유지한다.

| 시작 방식 | 사람 판별 모델 없음 | 사람 판별 모델 사용 |
| --- | --- | --- |
| 실측 `measurement` | 0.50 / 0.20 | 0.70 / 0.35 |
| 재생 `replay` | 0.50 / 0.20 | 0.70 / 0.35 |
| 수동 `manual` | 0.70 / 0.35 | 0.70 / 0.35 |
| 경보 `alarm` | 0.70 / 0.35 | 0.70 / 0.35 |

`GET /api/model/card?source=measurement`처럼 시작 방식을 지정하면 실제 적용 기준이 `runtime.thresholds`에 나온다. 모든 방식의 기준은 `runtime.thresholds_by_source`에 나온다. 기존 API 호환을 위해 생략 시 `manual`을 기준으로 반환한다. 학습 카드에 저장된 평가 수치와 현재 실행 기준도 구분해 설명한다.

### 3-2. 첫 감지 기록과 화면이 다른 계산 사용

경보·수동 상황의 첫 감지는 단일 창 값으로 기록했지만, 화면은 최근 판단의 지수평균으로 상태를 표시했다. 예를 들어 0.20 다음에 0.80이 들어오면 화면 평균은 0.50인데 첫 감지 기록은 먼저 생길 수 있었다.

모든 시작 방식에서 화면과 첫 감지 기록이 같은 최근 12개 창, 평균 계수 0.5, 저품질 제외와 반올림 기준을 사용하도록 맞췄다. 순간적인 한 창의 값과 화면 상태가 서로 다른 뜻으로 기록되는 것을 막는다.

### 3-3. 실측 중 실제 경보가 와도 실측으로 남음

기존 `open_incident()`는 활성 상황이 있으면 바로 반환했다. 실측 중 실제 `fire` 경보가 와도 `source=measurement`가 유지돼 실제 경보에 적용할 기준과 수신 기록이 제대로 전환되지 않았다.

수정한 동작은 다음과 같다.

- 실제 경보를 받으면 실측·수동 상황을 같은 ID의 `alarm`으로 전환한다.
- `mode_changed`와 `alarm_received`로 전환과 수신을 기록한다. 반복 경보도 매번 수신 이력을 남긴다.
- 실측에서 전환할 때는 이전 판단·첫 감지 이력을 삭제하지 않는다. 다만 `detection_reset` 이후의 데이터만 현재 운영 판단과 첫 감지에 사용한다. 전환 전에 쌓인 묶음 데이터도 현재 감지 계산에 섞지 않는다.
- 수동 상황은 이미 같은 운영 기준을 사용하므로 경보로 전환해도 기존 판단을 유지한다.
- 이미 경보인 상황을 실측·수동 요청으로 낮추지 않는다.
- `event=test`는 `alarm_test`로 기록하고 실제 화재로 승격하지 않는다. 상황이 없으면 수동 훈련 상황으로 연다.
- 녹화 시연이나 재생 상황에 실제 화재 경보를 연결하는 요청은 HTTP 409로 명확히 거절한다.

검증: `tests/test_detection_policy.py` 19개, `tests/test_mode_transitions.py` 12개. 네 시작 방식과 모델 유무, 화면·안내·첫 감지의 일치, 품질 반올림 경계, 전환 전 묶음 데이터 제외, 시험 경보와 반복 수신을 확인했다.

## 경보 모드는 무엇인가

경보를 받아 감지를 시작하는 `alarm` 경로와 `POST /api/alarm`은 이전 코드부터 있었다. 이번에는 실측 중 경보가 올 때의 전환과 기록을 보완했다.

흐름은 '외부에서 화재 경보 발생 → 건물 경보 토큰으로 API 호출 → 상황 개시 또는 경보 전환 → CSI로 구역별 기척 분석 → 지휘 화면에 상태·근거·우선순위 제공'이다. 이미 사전에 만든 빈 방 기준선이 있어야 해당 노드의 정상 분석이 가능하다.

경보 모드는 상황의 시작 방식이고, `change`/`person`은 사람 판별 모델 유무에 따른 분석 방식이다. 경보 모드가 됐다고 사람 판별 모델이 새로 생기는 것은 아니다.

현재 저장소에는 화재 수신기에 붙이는 실제 연동 장치가 없다. README에 적힌 것처럼 시연은 API를 직접 호출해 경보를 재현한다. Wi-Fi로 화재 자체를 판별하거나 119에 신고하거나 사이렌을 울리는 기능을 이번에 추가한 것은 아니다.
